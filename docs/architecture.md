# アーキテクチャ

状態: 2026-11-08 に確定した版 (白井さん)。決めた理由・比べた候補・試した結果は `docs/tech-decisions.md`、プロダクトの全体像は `docs/concept.md`、構成図は `docs/architecture.html` (画像は `docs/architecture-diagram.png`)。「仮決定」の項目は、実際の写真で試した結果で中身を見直す。

## 1. 何を成り立たせる設計か

```
見られる側: 朝、今日の全身写真を撮る → サーバで頭を塗り背景を消す → 服を 1 着ずつ切り抜く → 手持ちに入る
            → 今日の公開を選ぶ → ポケットの中で匿名 ID を発信し続ける (24 時に自動で切れる)
見る側:     街で服が目に入る → アプリを開く → 直近 5 分に受け取った ID をサーバで今日の着姿に変える
            → 気になる服を選ぶ → 手持ちと照合 → 合う組み合わせと理由 / 足りない 1 着 → 自分の着用イメージ
```

技術の山は 3 つ。

1. 近くの端末を、匿名のまま、ポケットの中でも検出する (BLE)
2. 全身写真から頭と背景を除き、重ね着も含めて服を 1 着ずつ切り抜く (Gemini が服を見つけて指示し、SAM 2.1 が形を取る)
3. 見つけた服を手持ちと照合し、組み合わせと着用イメージを出す (Gemini + Nano Banana 2.1)

## 2. 構成

```
Android アプリ (Flutter 3.47)                       審査員向け Web デモ (Flutter Web、Firebase Hosting)
  ├ Kotlin の常駐サービス (connectedDevice 型)         ├ 匿名ログイン、デモ用のデータだけ
  │   ├ BLE の発信: 匿名 ID (11 バイト、5 分で交換)      ├ 見る人は模擬の人物 (AI で作った架空の人物)
  │   └ BLE の受信: 直近 5 分を端末のメモリに保持        └ 近くの人の検出だけ模擬 (画面に「模擬」と書く)
  ├ Firebase Auth (Google ログイン、審査用のメールとパスワード、Web デモは匿名)
  └ Firestore の jobs を購読 (進み具合と結果を読むだけ)
        │ HTTPS + Firebase の ID トークン (両方のサービスで検証)
        ▼
Cloud Run (asia-northeast1、FastAPI、専用のサービスアカウント、鍵なし。vision は CPU 常時割り当て、api は処理中だけ)
  ├ vision (重い: 4 vCPU・8 GiB、普段は 0 台から起動)
  │   └ 元の写真を受ける (保存しない) → 頭を塗る → 顔が残っていないか確かめる → 背景除去 (isnet)
  │     → Gemini で服の名前・重ね着・枠・点 → SAM 2.1 tiny で服の形 → Storage と jobs に結果
  └ api (軽い: 1 vCPU・512 MiB、提出から審査の終わりまで最小 1 台)
      ├ 匿名 ID の発行 (公開時にその日の分) と、ID → 今日の着姿 (1 日 1 回、お互いさま、デモ用の例外)
      ├ 手持ちと今日の着姿の登録、照合、着用イメージ、ブロックと通報
      └ Firestore の書き込み (jobs 以外は全部ここ)、画像を返す
        │
        ├ Agent Platform (global): gemini-3.8-flash / gemini-nano-banana-2.1 (後で gemini-embedding-2)
        ├ Firestore ((default)、Standard、asia-northeast1)
        └ Cloud Storage for Firebase (アプリからの直接の読み書きは拒否)
```

デプロイは手で `gcloud builds submit` と `gcloud run deploy` を流す (`docs/runbook.md` の 1 節)。Web は `scripts/deploy_web.sh`。

## 3. 処理の流れ

### 3.1 今日のコーデの登録 (見られる側)

`vision` は処理が終わってから (15〜25 秒) 応答する。進み具合はアプリが `jobs` を購読して出す。

| 段 | サービス | 読む | 書く |
|---|---|---|---|
| 1. 全身写真を撮って確認し、「投稿」で送る。`jobId` はアプリが作り、送る前に `jobs/{jobId}` の購読を始める | アプリ → `vision` | — | — |
| 2. 背景を isnet で消す。透過を 2 値にし、一番大きい塊だけを残す (頭を塗るのに人物の形が要るので先に行う) | `vision` | 元の写真 (メモリ) | `jobs` (進み具合) |
| 3. 顔を隠す (2026-11-09 に変更): YuNet で顔が見つかった時は、顔 (目から顎まで) の楕円だけを強くぼかす (髪は残す)。顔が見つからない時 (横顔・うつむき・後ろ姿) は、頭の形に沿って頭を塗る | `vision` | — | — |
| 4. 顔を隠し背景を白にした画像 (Gemini に送る画像そのもの) で、YuNet で顔を探し直す (しきい値 0.3)。自分でぼかした楕円の中の検出は隠し済みとして数えない (色を残したぼかしは顔らしい形として拾われるため。2026-11-09 白井さんの判断)。それ以外の所に顔が残っていたら、ぼかしを段階的に強め、最後は頭の形に沿って塗る。それでも残る時だけ止めて、公開させない。見つかった顔がどれも人物の形の上 4 割に無い時 (服の柄の顔だけを拾った恐れ) は、頭も塗る | `vision` | — | `jobs` (失敗の理由) |
| 5. `gemini-3.8-flash` に、服ごとの区分・カテゴリ・重ね着 (外側 / 内側 / 単体)・色・柄・素材の推定・枠・服の上の点 2〜3 個を構造化出力 (`response_schema`) で返させる。SAM の画像の読み込みは、この応答待ちに重ねる | `vision` | 頭と背景を消した画像 | — |
| 6. 枠と点を SAM 2.1 tiny に渡して服の形を取り、透過の切り抜きにする。どの服でも、その服の点を「含める」、ほかの服の点を「除く」 | `vision` | — | — |
| 7. 処理後の着姿と切り抜きを置き、結果を書く。アプリは処理完了をユーザーに通知し、通知が使えない場合もアプリ内で知らせる | `vision` | — | Storage、`jobs` |
| 8. 通知後に本人が結果を確かめ、手持ちと今日の着姿に登録する (同じ服の判定は後に回す。入るまでは服をそのまま手持ちに足す) | アプリ → `api` | `jobs` | `wardrobeItems`、`dailyOutfits` |
| 9. 本人が今日の公開を選ぶ (**初期は非公開**)。`api` がその日の匿名 ID (5 分ごと、288 個) を発行して端末に渡し、端末が発信を始める。24 時に自動で切れる | アプリ → `api` | — | `broadcastIds`、`dailyOutfits` |

### 3.2 検出 (端末どうし)
- 見られる側: 接続しない BLE の発信に、128 ビットの UUID の ServiceData として「匿名 ID 11 バイト + 送信の強さ 1 バイト」を載せる。ID は 5 分ごとに、サーバから受け取った次の物へ替える (固定だとアプリの外から行動を追える)。画面オフの間も常駐サービスの中で続ける
- 見る側: 常駐サービスで受信を続け、直近 5 分 (設定で変えられる) を端末のメモリに持つ。サーバに送るのは、アプリを開いて見る時だけ
- 電波の強さは門にしない。受け取った新しさと近さの順に並べる、明らかに弱い物 (例 -90 dBm 未満) だけ外す、送る側の強さで機種の差を補正する、の 3 つにだけ使う
- 実測: 画面を消してポケットに入れた S25 Ultra の発信を、1〜2 m の Note10+ が 10 分間受け続けた (受信の間隔は最長 9 秒)

### 3.3 近くの人の着姿を見る (`api`)
1. アプリが受け取った匿名 ID の一覧を送る
2. サーバが ID をその日の公開の着姿に変える。受け付けるのは、ID の 5 分の枠が終わってから 20 分以内の物 (画面オフの間は交換が 10〜15 分おきに遅れるため)
3. 見る人も今日公開している時だけ返す (お互いさま)
4. 同じ人の着姿は、見る人ごとに 1 日 1 回だけ返す。記録は HMAC (見る人, 見られる人, 日付) の値だけ。日付ごとに分けて置き、今は消していない (値から組は読めない)
5. デモ用の uid (`DEMO_UIDS`) は 2〜4 の判定から外し、日付も問わずに返す。管理用の窓口でデモ用の記録を消せる
6. ブロックした相手は返さない
7. 返すのは、頭と背景を消した着姿の画像と服の情報、応答ごとの使い捨てのカード ID。距離と方向、手持ちの服の id は返さない
8. カード ID は見てから 30 分使える (照合・着用イメージ・ブロック・通報はカード ID で受ける)

### 3.4 手持ちとの照合 (仮決定、`api`)
フレンドの今日の公開コーデからも照合できる。選んだ服について、承認済みの関係と当日の公開状態を確認して照合用の使い捨てカードを発行する。服の id や uid は返さない。カードは最大 30 分で、日付が変わった時、フレンド解除、非公開、対象の服の変更でも使えなくする。フレンドの閲覧は近接検出の 1 日 1 回の記録や閲覧数を増やさない。

1. 見る人の手持ちを新しい順に 30 着まで集める。見た服と同じ区分も入れる (似た服をもう持っているかを見るため)。組み合わせの結果からは、見た服と一緒に着ない区分 (同じ区分、ワンピースとトップス・ボトムス) を外す
2. 見た服と手持ちの切り抜きに id の文を付け、`gemini-3.8-flash` に 1 回で見せる
3. 色・スタイル・場面・季節・素材・バランスの 6 観点で採点させ、合う組み合わせ 3 つ・理由・足りない 1 着・似た服をもう持っているかを返させる。返った id が渡した一覧に在るかを確かめる
4. 組み合わせる側が 30 着を超えた時か 1 回が 10 秒を超えた時は、Gemini が書いた「合う 1 着」の説明文をベクトルにして手持ちから引く形に切り替える (後に回す)

### 3.5 着用イメージ (仮決定、`api`)
1. 見る人本人の全身写真 (素顔のまま、アプリかブラウザのカメラで撮った物。Web デモの審査員は自分の写真か、デモの見る人の写真) と、見た服 + 選んだ手持ちの切り抜き (2〜3 枚) を `gemini-nano-banana-2.1` に 1 回で渡す
2. 2 着同時で崩れたら、1 着ずつ 2 回の編集にする
3. 本人にだけ返し、「AI による着用イメージ」と表示する
4. 1 回約 18 秒 (試験の値)。デモの人物でも毎回その場で作る (2026-11-10 に変更。事前に生成した画像は AI を止めた時だけ「事前に作った」と出して返す)
5. 画像の生成はモデルごとに 1 分 2 回まで (Google の決めた上限で、申請で増やせない。2026-11-08 に割り当ての画面で確認)。`gemini-nano-banana-2.1` が 429 なら予備の `gemini-3-pro-image` で作り (合わせて 1 分 4 回)、それでも 429 なら少し待ってやり直し、だめなら 502

### 3.6 同じ服の判定 (`api`、2026-11-08 に作った)
1. 手持ちに入れる時 (PUT /v1/outfits/today) に、切り抜きを `gemini-embedding-2` (1536 次元) でベクトルにして手持ちの文書に置く (作れなくても登録は止めない)
2. S9 で GET /v1/jobs/{jobId}/same-items を呼ぶと、処理の結果の服ごとに、本人の手持ちの同じ区分からベクトルの近い 5 着を出す。1 人の手持ちは数十着なので、Firestore のベクトルの索引 (`find_nearest`) は使わずに api の中で比べる
3. 5 着を `gemini-3.8-flash` に見せ、同じ 1 着か「どれでもない」を選ばせる。渡していない id は捨てる
4. 「これでは?」と出し、まとめるかは本人が 1 タップで決める (PUT の `sameAs`)。Gemini が「どれでもない」と言った服は聞かずに新しい服にする
5. Gemini が混んでいると (共有の容量の 429) 1 分ほどかかることがある。画面は待つ間「確かめています」と出す

## 4. データ

| 置き場 | 主な項目 | アプリから |
|---|---|---|
| `users/{uid}` | 公開の設定、身長や体型 (任意、本人の入力だけ) | 本人が読む |
| `users/{uid}/wardrobeItems/{itemId}` | 区分、カテゴリ、属性、切り抜きの場所、(後で) ベクトル 1536 次元 | 本人が読む |
| `users/{uid}/dailyOutfits/{date}` | 処理後の着姿の場所、その日の服の id、コーデ専用メモと写真のないアイテムのメモ、公開か、公開の終わり (24 時) | 本人が読む |
| `users/{uid}/jobs/{jobId}` | 登録の進み具合と処理の結果 (`vision` が書く) | 本人が読む |
| `broadcastIds/{id}` | 匿名 ID、5 分の枠、対応する着姿 | 読めない |
| `viewLog/{date}/v/{hmac}` | 1 日 1 回の判定。日付ごとに分けて置く (消す処理は作っていない。値は HMAC で、組は読めない) | 読めない |
| `cards/{cardId}` | 使い捨てのカード ID と、対応する着姿・服・持ち主と見た人の uid (30 分で切れる。切れた後も文書は残り、消す処理は作っていない) | 読めない |
| `blocks`、`reports` | ブロックと通報 | 読めない |
| `quotas/{uid}` | その日の呼び出しの回数 | 読めない |
| Storage `users/{uid}/...` | 処理後の着姿、服の切り抜き、着用イメージ用の自分の写真 (本人が消せる) | 読み書きできない (`api` が返す) |

書き込みは `api` が行う (例外は `vision` の `jobs` と Storage の処理後の画像)。Security Rules で、アプリからは本人の文書を読むことだけを許し、Storage は全部拒否する。ストレッチ (確かめた記録、保存、似た人を上に並べる、いいね) は `wardrobeItems` と投稿を分けておけば後で足せる。

## 5. 安全

- **原則: 目で見えている以上のものは見る側に渡さない**。見せるのは、本人が公開を選んだ今日の着姿 (頭と背景を消した物) と服の情報だけ。名前、プロフィール、過去の投稿、距離、方向は出さない
- 同じ人の着姿は見る人ごとに 1 日 1 回。見えない所の特定の人が「まだ近くにいるか」を確かめる使い方を防ぐ。1 日 1 回の記録 (`viewLog`) には、誰が誰を見たかの組を素のまま残さない。ただし使い捨てのカード (`cards`) は、30 分で切れた後も持ち主と見た人の uid を持ったまま残る (今後 Firestore の TTL で消す。どちらも利用者からは読めない)
- お互いさま: 見る人も今日公開している時だけ見られる
- 匿名 ID は 5 分で替わり、ID と本人の対応はサーバだけが持つ。見る側に渡すのは使い捨てのカード ID で、日をまたいで続く id は渡さない
- 公開は本人が手で始め、24 時に自動で切れる。ブロックと通報を用意する
- ベクトルの検索は必ず本人の手持ちに絞る。他人の服を横断して探さない (服で人を探す機能にしない)。カメラで相手を照合する機能は作らない
- 元の写真はサーバのメモリの中だけで扱い、保存しない。顔は常にぼかすか塗り (顔が見つからない時は頭を塗る)、隠した後に (ぼかした所の外に) 顔が残っていたら Gemini に送らず公開もしない
- 着用イメージに使う自分の写真は素顔のまま送るが、生成した画像は本人にしか返さない。写真はアプリ (Web はブラウザ) のカメラで撮った物だけ (他人の写真で生成させないため)。Web デモの審査員 (匿名) の写真と着用イメージは Storage の `anon/` の下に置き、1〜2 日で消す (Storage の決まりは日単位)。デモの架空の人物の写真だけは、スクリプトで直接入れる例外
- 他人の着姿は Storage の URL では渡さず、`api` が画像のバイトで返す (透かしは 2026-11-08 にチームの判断で外した。漏れた画像を辿る手順は無く、画面の保存は Android で止め、カードは 30 分で切れるため)。画面の保存をなるべく防ぐ (着姿の画面に FLAG_SECURE)。連絡・フォローの機能は作らない
- アプリは Google ログイン。審査員向けにだけ、メールとパスワードの審査用アカウントを用意した (誰でも作れる登録の口は無い)。Web デモは匿名でデモ用のデータだけ。`vision` と `api` の両方で ID トークンと回数の上限を確かめる
- ログに ID トークン・匿名 ID・素の uid を書かない
- 公開の提出用リポジトリに、顔の写る写真と Commons の写真を入れない。Firebase のクライアント用のキーは、ドメインと API を制限する

## 8. 今回作らないもの

外部 EC との連携、型番の特定、独自モデルの学習、ポイントと通貨、相手への連絡機能、カメラでの照合、iPhone からの発信、自宅などの場所の判定。

いいね (11/9 に実装): 近くのコーデのいいねは、持ち主に「近くの人から」とだけ通知し、誰からかは出さない (相手への連絡の手段にはしない)。フレンドのいいねは名前を出す。同じ人・同じコーデからの通知は 1 日 1 回。コメント・コミュニティ・トレンドは作っていない。
