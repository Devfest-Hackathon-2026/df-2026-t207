アーキテクチャ

街ですれ違った人の今日の服を、話しかけずに見て、自分の手持ちで合うか確かめる

3 つの流れ

1. 今日のコーデの登録 (見られる側)

  1. 全身写真を撮る端末
  2. vision が頭を塗り、顔が残っていないか確かめ、背景を消すvision
  3. Gemini が服を見つけ、名前・重ね着・枠・点を返すGemini
  4. SAM 2.1 が服 1 着ずつの形を切り抜くvision
  5. 結果を確かめて手持ちに入れるapi
  6. 今日の公開を選ぶと、その日の匿名 ID を受け取り、発信が始まる (24 時に切れる)端末

試験の値: 背景 2.5 秒 + Gemini 9〜28 秒 + SAM 4 秒

2. 近くの人の着姿を見る (見る側)

  1. 街で服が目に入る。相手の端末はポケットの中で発信しているBLE
  2. アプリを開くと、直近 5 分に受け取った ID を送る端末
  3. api が ID を今日の着姿に変えるapi
  4. 新しく近い順に並ぶ。距離と方向は出ない端末

実測: 画面を消してポケットに入れた端末を 10 分間受け続けた (間隔は最長 9 秒)

3. 手持ちで合うか確かめる (見る側)

  1. 気になる服を選ぶ (見てから 30 分使える)端末
  2. 手持ちの合わせる側の服 (30 着まで) と一緒に Gemini が採点するGemini
  3. 合う組み合わせ 3 つと理由、無ければ足りない 1 着api
  4. 似た服をもう持っていれば「買わなくて済む」と出すGemini
  5. 自分の写真に着せた着用イメージ (本人にだけ、AI と明記)Nano Banana

試験の値: 着用イメージ 1 回 約 18 秒。デモの見せ場は事前に生成した画像

安全の決まりがどこで効くか

決まりどこで
目で見えている以上は見る側に渡さないapi が返すのは本人が公開した今日の着姿 (頭と背景を消した物) と服の情報だけ
見えない所の特定の人を追わせないapi: 同じ人は見る人ごとに 1 日 1 回。匿名 ID は 5 分で替わり、見る側には使い捨てのカード ID だけ
元の写真を残さないvision のメモリの中だけ。Storage には処理後の物だけ
顔を外に出さない頭は常に塗り、塗った後に顔が残っていたら Gemini に送らず公開もしない
服で人を探させないベクトル検索は本人の手持ちだけ。カメラの照合は作らない
なりすましで条件を破らせないアプリは Google ログイン (審査員向けにだけメールとパスワードの審査用アカウント)。Web デモはデモ用のデータだけ。着用イメージの写真はアプリのカメラで撮った物だけ

なぜこの構成か

選んだ物理由
素の BLEポケットの中で接続も承認も無しに ID を渡せる。画面オフで動くと実機で確かめた
Flutter + KotlinAndroid と Web デモで画面を共有。常駐の BLE だけ Kotlin
Gemini + SAM 2.1服の名前と重ね着は Gemini、形は SAM。服専用の公開モデルは重ね着を分けられず、重みが非商用だった
Nano Banana 2.13 つ試して、元の服を残したまま羽織らせられたのはこれ。1 組約 6 円
Cloud Run を 2 つに分ける審査の間 URL を動かし続ける決まり。軽い api だけを常に起こし、費用を抑える
画像の処理をサーバに置く処理を 1 か所にまとめ、写真をまとめて流して試せる

秒数はチームの PC で試した値で、Cloud Run の上では未確認。2026-11-08 時点。詳細は docs/architecture.md、決めた理由は docs/tech-decisions.md。ロゴは各社の公式の物 (svgl、Google Cloud product icons、Lucide) で、各社の商標
