## 1. 端末どうしの検出 (仮決定、実機の結果で確定)

満たしたいこと: 見られる側はポケットの中で発信を続ける / 接続や承認の操作なしで匿名 ID を受け取る / 数秒で見つかる / 人混みでも動く。

- 本線: 素の BLE。見られる側は、接続しない BLE の発信 (英語で advertising。宣伝の意味ではなく、周りに小さな知らせを定期的に出すこと) で匿名 ID を出し、常駐のサービス (connectedDevice 型) の中で続ける
- 発信の中身: 128 ビットの UUID の ServiceData に、**匿名 ID 11 バイト + 送信の強さ 1 バイト**。UUID と ID で 30 バイトになり、通常の発信の上限 31 バイトに TX Power の項目 (3 バイト) は入らないため (レビューの指摘で 12 バイトから変えた)
- 匿名 ID: サーバ (`api`) が、本人が公開を選んだ時にその日の分 (5 分ごと、1 日 288 個) をまとめて発行し、端末に渡す。端末は通信が止まる画面オフの間もそれを使い、替える時はその時刻の枠の ID を選ぶ (タイマーが遅れても、枠と ID がずれないように)。5 分ごとに替えるのは、電波はアプリの外からも見えるため、固定だと行動を追跡されるから。替える時は発信を止めて始め直す。公開はその日の 24 時に自動で切れる
- 受信: 常駐のサービスで受信を続け、**直近 5 分** (設定で変えられる) を端末のメモリに持つ。サーバには、アプリを開いて見る時だけ送る
  - 5 分にした理由 (2026-11-08 白井さん): 見えない所に行った人が一覧に並ぶ害より、見たいと思った人が一覧に出ない方が体験として大きなマイナス。ほかの守り (1 日 1 回、距離と方向を出さない、公開は本人が選ぶ、ID は 5 分で替わる) があるので、並ぶ害は小さい。ID を替える間隔と揃えると「この 5 分にすれ違った人」と説明できる
  - 一覧は、受け取った新しさと電波の強さの順に並べる。人混みでも直前にすれ違った人が上に来る
  - サーバが受け付ける ID: その ID の 5 分の枠が終わってから 20 分以内。画面オフ (Doze) の間は 5 分ごとの交換のタイマーが 3〜12 分遅れ、1 つの ID が 15 分ほど出続けることが実測で分かったため (下の実測)。受信の 5 分を足して 20 分にした
- 対象: 見られる側は Android だけ (iOS は裏で発信すると Android から見えない)
- Nearby Connections と比べた (2026-11-08 夜、同じ 2 台、画面オフ、下の実測)。どちらも画面オフで動き、電池の差も小さかった。**BLE のままにする**: 受け取るたびに電波の強さが取れ (並び順と機種差の補正に使う)、受信の間隔も 1 回ごとに見える。Nearby は見つけた時と見失った時の 2 つの知らせだけで、電波の強さが取れない。Android 12 では位置情報のスイッチも要る
- 検証用アプリ: `poc/ble/` (手順は `poc/ble/README.md`)。開発開始 (11/5) の後に書いたので、アプリの android/ に移してよい
- 実測 (2026-11-08 00:00〜00:10): S25 Ultra を画面オフ (Dozing) でポケットに入れて発信、1〜2 m の Note10+ が受信。10 分間止まらず、1 分あたり 15〜33 回受信、受信の間の最長は 9 秒。電波の強さは -60〜-66 dBm。「画面オフ・ポケットの中で発信が続くか」は合格
- 電池 (2026-11-08 02:53〜04:54、S25 Ultra、充電なし・画面オフ、1 時間ずつ): 電池の残量計 (charge counter) の減りは、アプリなしで 117 mAh、BLE で発信して 117 mAh と同じだった (電池の % は 3 と 2)。`batterystats` が検証用アプリに付けた分は 1 時間で 0.12 mAh。**BLE の発信の電池の負担は、端末の待機の減りに埋もれるほど小さい**。ただしこの試験では、無線の adb (Tailscale 経由) がつながったままで、待機の減り (約 117 mAh/時) は普段より大きい。結果の置き場は `%LOCALAPPDATA%\df-hack26\ble-poc-results\night-1108\`
- Nearby (2026-11-08 05:57〜07:18、S25 が画面オフで発信、Note10+ が受信): 1 回目 (02:32〜) は S25 (Android 16) で発信に失敗していた (`MISSING_PERMISSION_ACCESS_WIFI_STATE`、検証用アプリが Wi-Fi の状態の権限を Android 12 以下にだけ宣言していた)。宣言を直した 2 回目は、始めてすぐ見つけ、20 分間見失わなかった (ID を替えた 06:13 に、見失いと見つけ直しが 0.02 秒の間に続いた)。電池は 1 時間で 127 mAh (アプリなし 117、BLE 117)、`batterystats` が付けた分は 0.11 mAh
- ID の交換の遅れ (S25 の記録の `id_rotate`): 画面を消して Doze に入ると、5 分ごとのタイマーが 150〜690 秒遅れ、交換は 10〜15 分おきになった (BLE でも Nearby でも同じ)。設計で、端末はその時刻の枠の ID を選び、サーバは枠の後 20 分まで受け付ける形にした。もっと正確に替えるには `AlarmManager` の `setExactAndAllowWhileIdle` が要るが、Doze の間は約 9 分に 1 回までしか起きられない
- まだ確かめていないこと: 見る側を画面オフにした時の受信 (フィルタ付きの受信は 10 分で省電力のモードに落ちる)、距離 (1 / 5 / 10 m)、見つかるまでと消えるまでの秒数、すれ違ってからアプリを開くまでの秒数

| 比べた候補 | 分かったこと | 判断 |
|---|---|---|
| Nearby Connections | 発見時に endpointInfo で ID を渡せる。Google の技術。Flutter プラグインは Android のみで更新なし。探索は無線の負荷が高い。RSSI が取れない | 実機で比べる |
| GPS の位置と時刻の一致 | Web でも動くが、目の前の人を区別できる精度が無い | 捨てる |
| Nearby Messages | 非推奨で削除予定 | 捨てる |

## 2. アプリの土台 (確定 2026-11-08)
- 決定: Flutter。常駐の発信と受信だけを、同じアプリの android/ に Kotlin の foreground service (connectedDevice 型) で書き、MethodChannel / EventChannel でつなぐ
- 確かめた: Flutter 3.47.9 で、Firebase (core・auth・Firestore・Storage)・google_sign_in・image_picker・ML Kit・http を全部入れた空のアプリが、`flutter build apk --debug` と `flutter build web` の両方で通った。逃げ道 (Kotlin Compose) は使わない
- 理由: 画面を Android と審査員向けの Web デモ (Firebase Hosting) で共有できる。Flutter・Dart・Firebase がすべて Google の技術。常駐の発信はどの土台でも Kotlin が要る
- 比べた候補: Kotlin (Compose) は一番素直だが Web を別に作る。Kotlin Multiplatform は Web が Beta で Firebase が有志の SDK。React Native は常駐を結局 Kotlin で書き、Google 技術の話にならない
- 使わないもの: `flutter_blue_plus` (営利の利用は有料)、`flutter_background_service` (2024-12 から更新なし)、Flutter の `nearby_connections` (Android のみ、更新なし)
- 注意: Android のビルドに「Kotlin の Gradle プラグインの古い使い方」の警告が出る (プラグイン側の問題で、今はビルドを止めない)。初回の APK のビルドは 13 分かかった。3 人とも Flutter を 3.47.9 に揃える

## 3. 匿名 ID と安全 (決定)
- 原則: 目で見えている以上のものは、見る側に渡さない
- 人数の条件 (周りに 3 人以上) は置かない。着姿を見せる以上、人数では誰の着姿かを隠せないため
- 同じ人の着姿は、見る人ごとに 1 日 1 回だけ出す。見えない所にいる特定の人が「まだ近くにいるか」を確かめる使い方を防ぐ。つきまといを防ぐための要となる対策
  - 記録は「見る人・見られる人・日付」を秘密の鍵で HMAC にした値だけを持ち、日付ごとに分けて置く (消す処理は今は無い)。この記録からは誰が誰の近くにいたかの組は読めない。ただし使い捨てのカード (`cards`) には持ち主と見た人の uid が残る (architecture の 5 節)
- お互いさま: 見る人も今日公開している時だけ見られる
- 例外: デモ用の uid (許可リスト `DEMO_UIDS`) は、日付・1 日 1 回・お互いさまの判定から外す。デモ用の uid の記録を消す管理用の口も作る。審査期間 (11/11〜) と当日の練習でデモが出なくなるのを防ぐため (レビューの指摘)
- 電波の強さは門にしない。端末・持ち方・体の向きで大きく揺れ、厳しい閾値だと近くの人が出ず反応も遅れるため。使い方は 3 つ: 近そうな順に並べる / 明らかに弱いもの (例 -90 dBm より弱い) だけ外す / 発信に載せた強さで送る側の機種差を補正する
- 見る側に返すのは、応答ごとの使い捨てのカード ID。手持ちの服の id は渡さない (日をまたいで同じ id が出ると同じ人だと分かるため)。照合・着用イメージ・ブロック・通報はカード ID で受ける。カード ID は見てから 30 分で切れる (着用イメージの生成に約 18 秒かかるので、離れた後も少し使えるようにする)
- 公開は本人が手で始め、その日の 24 時に自動で切れる。自宅などの場所を判定する機能は作らない
- ブロックと通報: 最小の形で作る (Firestore に 1 件書き、ブロックした相手は以後返さない)
- ログに ID トークン・匿名 ID・素の uid を書かない (書くと誰が誰の近くにいたかが Cloud Logging に残る)

## 4. 画像の処理 (決定 2026-11-08、骨格は B)
- 流れ (全部 `vision` の中、メモリの上だけ):
  1. アプリから元の全身写真を受ける (保存しない)
  2. 頭を塗る: 人物の形の上から 1/6〜1/5 の帯と、YuNet (OpenCV、MIT) で見つけた顔の枠を 1.8 倍に広げた範囲の、両方を常に塗る
  3. 塗った後にもう一度 YuNet で顔を探す。**顔が残っていたら Gemini に送らず、公開もさせない**
  4. 背景を消す: isnet-general-use (rembg)。透過の値を 2 値にし、一番大きい塊だけを残す (通行人や柱が半透明で残るのを消す)
  5. 頭と背景を消した画像を `gemini-3.8-flash` に渡し、服ごとの名前・区分・重ね着 (外側 / 内側 / 単体)・色・柄・素材の推定・枠・服の上の点 2〜3 個を構造化出力 (`response_schema`) で返させる
  6. 枠と点を SAM 2.1 tiny に渡して服ごとの形を取り、透過の切り抜きにする。どの服でも、その服の点を「含める」、ほかの服の点を「除く」として渡す
  7. 処理後の着姿と切り抜きを Storage に書き、結果を `jobs` の文書に書く。手持ちと今日の着姿への登録は、アプリがその結果で `api` を呼んで行う
- 役割の書き方 (提出ドキュメントと構成図): どの服をどこで切るか、重ね着の外と内は Gemini が決める。SAM はその指示で形を取るだけ。理由は記録済みの事実で書く: Gemini 3.x は領域分割に対応していない / `gemini-2.5-flash` と Robotics-ER 1.6 の分割はこのプロジェクトから 404 だった / サーバで処理するのは写真をまとめて流して試せるから
- 理由: SAM を Cloud Run の Python で動かす以上、背景除去も同じ所に置けば処理が 1 か所にまとまり、手元の PC で写真をまとめて流して試せる。端末で消す案 (A、ML Kit) の利点は「元の写真は端末から出ない」と言えることで、それは手放した。ML Kit には戻さない (2026-11-08 白井さん。Google の技術は中心の Gemini・Embedding・Nano Banana・Cloud Run・Firestore・Firebase で十分に使っている)
- 捨てた案: 服専用の SegFormer (`segformer-b3-fashion`、重ね着の中の服を 1 着として出せず、スカートをパンツとした。重みは非商用) / 枠 × 人物の形 (内側の服の枠が外側の服を含む) / Gemini の領域分割 (呼べない) / BiRefNet (CPU で 1 枚 30〜43 秒) / 画像生成で平置きに描き直す (実物と違う服になる恐れ)
- 逃げ道: `vision` のコンテナがビルドか配備で詰まったら、SAM を外し、Gemini の枠と isnet の人物の形の掛け合わせで切り抜く (重ね着の内側は粗くなる)
- 大きさは 4 vCPU・8 GiB: この PC では 8 スレッドにしても速くならなかった (isnet 2.5 → 3.0 秒、SAM 3.4 → 3.2 秒)。一番長いのは Gemini の応答待ち。GPU は Cloud Run の東京に無く、無料トライアルで枠が付かない見込み (未確認)。Cloud Run に載せた時に 4 vCPU と 8 vCPU を 1 回ずつ測る
- 速くする工夫:
  - SAM の画像の読み込み (約 3 秒) は Gemini の結果を待たずに始め、Gemini の応答待ちに重ねる (同じ `vision` の中で行うので成り立つ)
  - モデルの重みはコンテナに入れ、Cloud Run の起動時の CPU ブーストを使う (0 台からの起動は、直す前 101 秒 → 直した後 26 秒。2026-11-08 に測った。内訳は docs/runbook.md)
  - Gemini の思考の量 (thinking_level) は精度を測ってから決める。精度が落ちるなら下げない (2026-11-08 白井さん)
- ライセンス: SAM 2.1 (コードと重み Apache-2.0)、rembg (コード MIT)、YuNet (MIT)。**isnet の重みのライセンスは未確認** (元は xuebinqin/DIS)。著作物利用シートに書く前に確かめる
- 試した結果 (2026-11-08、Commons の CC BY-SA の写真 5 枚、この PC の i5 で 4 スレッド):
  - 背景除去: isnet 2.5 秒。BiRefNet lite 12.7 秒、BiRefNet 30 秒 (CPU では使えない)
  - Gemini 3.8 Flash: 1 回 9〜28 秒。重ね着の外と内を分けた (ベストの下の赤いニット、ジャケットの下の赤い服)。中の白い T シャツは出なかった。形式が正しくない JSON を返したことが 1 回あった
  - SAM 2.1 tiny: 画像の読み込み約 3 秒 + 全部の服で約 1 秒。服の上の点を渡すと、内側の赤いニットもきれいに切り抜けた
  - **限界**: この試験は頭と背景が残った元の写真で行った。頭を塗り背景を消した画像で同じ結果が出るかは、まだ確かめていない
- 試した物: `%LOCALAPPDATA%\df-hack26\seg-bench\` (提出用リポジトリには入れない)
- V2 の試験 (2026-11-08、`server/vision/masking.py`、テスト 4 つ): Commons の 5 枚で、isnet → 一番大きい塊 → YuNet で顔を探す → 頭を塗る → もう一度顔を探す、を通した。塗る前に見つかった顔は 0〜3 個 (通行人を含む)、塗った後は 5 枚とも 0 個。一番大きい塊を残す処理で、通行人と柱が消え主な 1 人だけになった。処理後の画像で Gemini と SAM を回し直し、元の写真の時と同じく重ね着 (ベストの下のニット、ジャケットの下の服) を分けた。SAM の秒数も同じ (読み込み約 3 秒 + 全部の服で約 1 秒)
- V1 (2026-11-08、`vision` を Cloud Run に配備、4 vCPU・8 GiB): ビルド 3 分 55 秒。モデルの読み込みは isnet 2.9 秒・SAM 1.3 秒・YuNet 0.1 秒。乱数の画像 (1920x1080) で isnet 2.5〜2.7 秒・SAM の画像の読み込み 3.1 秒 (1 回目だけ 3.3 秒と 5.2 秒)。手元の i5 とほぼ同じ。0 台からの起動の秒数は未測定。ビルドで要った物: `torchvision` (SAM の前処理)、既定のサービスアカウントへの `roles/cloudbuild.builds.builder`。`/healthz` は Cloud Run の予約の道でアプリに届かない

## 5-1. 同じ服の判定 (仮決定 2026-11-08、後に回す)
- 決定: 服の切り抜きを `gemini-embedding-2` (1536 次元) でベクトルにし、Firestore の `find_nearest` で「本人の、同じ粗い区分 (上衣・下衣・羽織・靴など)」に絞って近い 5 着を出す。5 着を `gemini-3.8-flash` に見せて 1 着か「どれでもない」を選ばせる。まとめるかは本人が 1 タップで決める。Gemini が「違う」と言い切った時は聞かずに新しい服として登録する
- **作る順番 (2026-11-08 白井さん)**: 中心の流れ (登録 → 見る → 照合 → 着用イメージ) が Web と実機で端から端まで通った後に着手し、11/9 18:00 までに入らなければ止める。入らない間は、登録した服はそのまま手持ちに入る
- 理由: 一番の危険は、似た別の服を同じ 1 着とする誤統合 (手持ちが乱れる)。LLM は「似ている」を過大評価すると報告がある (EcomEval、MMVM)。見逃し (同じ服が 2 枚に分かれる) は目に見えて後から直せる
- 捨てた案: ベクトルの閾値だけで決める (閾値を決める写真が足りない) / Gemini の「同じ」で自動統合 (実写真で誤統合 0 件の時だけ後で入れる) / 服用の公開モデル (Marqo-FashionSigLIP など、同じ 1 着を探す精度の数字が無い)
- 安全: ベクトルの検索は必ず本人の手持ちに絞る。他人の服を横断すると「服で人を探す」機能になる
- 調べた中身: `research/tech-stack/match.md`

## 5-2. 手持ちとの照合 (仮決定 2026-11-08、Gemini で試した結果で見直す)
- 決定: 見た服 1 枚と、組み合わせる側の区分の手持ちの切り抜きに id の文を付けて、`gemini-3.8-flash` に 1 回で見せる。色・スタイル・場面・季節・素材・バランスの 6 観点で採点させ、合う組み合わせ 3 つ・理由・足りない 1 着を構造化出力で返させる。返った id が渡した一覧に在るかをサーバで確かめる
- 同じ呼び出しで「似た服をもう持っているか」(買わなくて済む根拠) も返させる。5-1 のベクトルが入ったら、そちらで候補を出す形に替える
- 切り替え: 組み合わせる側の手持ちが 30 着を超えた時か、1 回が 10 秒を超えた時は、Gemini が「合う 1 着」の説明文を書き、それを `gemini-embedding-2` でベクトルにして本人の手持ちから `find_nearest` で引き、Gemini は組み合わせと理由を書くだけにする (TATTOO の形)。デモの手持ちは 30 着より少ないので、後に回してよい
- 理由: ベクトルが近いのは似た服で、合う服ではない。理由が出るので、点数ではなく理由を見て本人が決める画面にできる
- 捨てた案: ベクトルの近さを「合う」とする (根拠が無い) / 学習済みのコーデのモデル OutfitTransformer (学習データが EC の商品写真、理由を出せない) / 文章だけを LLM に渡す (穴埋めの正答 29%)

## 6. 着用イメージ (仮決定 2026-11-08、試した結果で見直す)
- 本線: `gemini-nano-banana-2.1` (Agent Platform、global)。**見る人本人の全身写真 (素顔のまま、アプリのカメラで撮った物)** と、服 2〜3 枚 (見た服 + 照合で選んだ手持ち) を 1 回で渡して着せる。2 着同時で崩れたら 1 着ずつ 2 回の編集に落とす
- 自分の写真は Storage の本人の場所に置き、`api` だけが読む。本人がいつでも消せる。生成した画像は本人にしか返さない
- 画像には「AI による着用イメージ」と出す。他人の写真で生成させないため、写真はアプリのカメラで撮った物だけ (D1)
- デモの人物でも毎回その場で作る (2026-11-10 に変更。事前に作った物を今作った物に見せないため。事前の画像は AI を止めた時だけ、そう表示して返す)
- 比べた候補: Nano Banana Pro (`gemini-3-pro-image`、忠実さが足りない時の上位) と Virtual Try-On (`virtual-try-on-001`、2026-09-14 に非推奨)。OSS (FASHN・Leffa・CatVTON など) は試さない (多くが非商用、東京に Cloud Run の GPU が無い)
- 試した結果 (2026-11-08、Commons の写真 1 組、背景を残し頭を塗った人物に SAM 2.1 で切り抜いたデニムジャケットを着せる): 3 つとも約 18 秒で生成できた。Nano Banana 2.1 は元のベスト・ニット・リュックを残して上に羽織らせ、刺繍まで再現した (切り抜きで欠けた部分も補った)。Pro は同等だが、背景の車に灰色の四角を勝手に足した。Virtual Try-On は新しいプロジェクトから東京で呼べたが、元のベストとリュックを消して置き換え、隣の人の服の色まで変えた。本線は Nano Banana 2.1 のまま
  - この試験では頭の位置を Gemini に聞いて塗った。製品では、着用イメージの自分の写真は塗らないので、この手順は使わない
- 調べた中身: `research/tech-stack/tryon.md`

## 7. サーバ (決定 2026-11-08)
- 構成: FastAPI を Cloud Run (`asia-northeast1`) の 2 サービスに分ける。どちらも Firebase の ID トークンを確かめ、利用者ごとと全体の 1 日の回数に上限を置く (`vision` は写真を送れば CPU と Gemini を使えるので、検証が要る)
  - `api` (軽い): 匿名 ID の発行と着姿への変換、手持ちと今日の着姿の登録、照合、着用イメージ、ブロックと通報。1 vCPU・512 MiB (処理中だけ CPU を割り当てる)。**11/10 19:00 の提出から審査が終わるまで最小 1 台** (予選 11/14 まで。決勝に進めば 11/27 まで)
  - `vision` (重い): 4 の処理 (頭・背景・Gemini の枠と点・SAM)。4 vCPU・8 GiB、最大 3 台。普段は 0 台から起動し (起動は約 26 秒、2026-11-08 に測った)、会場でデモをする当日だけ最小 1 台
- 書き込み: Firestore の書き込みは `api` が行う。例外は `vision` が書く `jobs` (進み具合と処理の結果) と、Storage の処理後の画像だけ
- 理由: 運営は「デプロイ URL が動き続けるように」(キックオフ [28:52])、「Regional Day まで動かし続けること」(Discord) と求めている。重い方を起こし続けると決勝まで約 2 万円 (概算)。審査員向けの Web デモはデモ用のデータを事前に登録しておくので、審査員がたどる「見る → 照合 → 着用イメージ」は `api` だけを通り、待たされない
- 元の写真: リクエストで `vision` に直接送り、メモリの中で処理して保存しない
- データ: Firestore の `(default)` (Standard、`asia-northeast1`) と Cloud Storage for Firebase。Storage はアプリからの直接の読み書きを全部拒否し、画像は `api` が返す (他人の着姿も画像のバイトで返す。透かしは 2026-11-08 に外した)
- Gemini: Gen AI SDK で Agent Platform の `global` を、Cloud Run 専用のサービスアカウントで呼ぶ。鍵は持たない
- 時間のかかる処理: リクエストの中で処理し、進み具合を `jobs` に書いてアプリが購読する。`vision` は CPU 常時割り当て (`--no-cpu-throttling`)、`api` は処理中だけの割り当て (要求の中で処理を終えるので足りる)。FastAPI の `BackgroundTasks` は使わず、リクエストの中で処理する方が単純なため。途中で切れる問題が出たら Cloud Tasks に切り替える
- 費用の歯止め: Agent Platform にだけ支出の上限 (spend cap) を掛ける (11/14、決勝に進めば 11/27 までの見込みで)。利用者ごとと全体の 1 日の呼び出し回数に上限を置き、環境変数 1 つで AI を止められるようにする。AI が止まった時、Web デモは事前に計算した照合結果と着用イメージを出す。Cloud Run には上限を掛けない (デモの URL ごと止まる)
- デプロイ: 手で `gcloud builds submit` と `gcloud run deploy` を流す (手順は `docs/runbook.md` の 1 節)。最初は `deploy.sh` とタグの push で動く Cloud Build を考えたが、作らなかった (時間)
- 捨てた案: Cloud Functions (関数ごとのデプロイで API の仕様を 1 枚にできない) / Genkit (Python は Beta) / ADK (処理の順番が決まっていて自律のループが要らない) / Cloud SQL (止めていても時間で課金) / Firebase Data Connect (覚える時間が無い) / 1 サービスで常に 1 台 (費用) / 1 サービスで 0 台から (審査員を 20 秒以上待たせる)
- 調べた中身: `research/tech-stack/backend.md`

## 8. 審査員向けのデモ (決定 2026-11-08)
- 事前審査で価値を伝える主役はデモ動画。実機の BLE の検出まで映す (運営: 予選のピッチに進めるかは提出物で決まる)。模擬・事前の生成・待ち時間の短縮を使った所は字幕で明記する (デモ動画の偽装は審査対象外)
- デプロイ URL: Flutter Web を Firebase Hosting に置いた模擬モード。ログインなし (匿名、D4) でデモ用のデータだけを使う。近くの人の検出だけを模擬し、画面に「模擬」と書く。照合と着用イメージは本物の Gemini を `api` 経由で呼ぶ
- Web デモの見る人: 匿名の審査員には手持ちも写真も無いので、模擬の見る人 (AI で作った架空の人物。手持ちと全身写真を事前に登録) として動く。照合と着用イメージは、この人物の手持ちと写真を使う
- Web の着用イメージ: 毎回その場で作る。匿名の審査員全員で 1 日の回数の上限を共有する (着用イメージ 300 回・照合 500 回)
- デモ用のデータ: `vision` の完成を待たず、手元の PC で同じ処理を流して Firestore と Storage に直接入れるスクリプトで作る
- 壇上: 2 台の Android で本物の BLE。失敗への備えは 4 段 (事前の登録 / 事前の生成 / 1 タップで模擬に切り替え / 録画)
- CI/CD: 開発用リポジトリに Cloud Build のトリガー (タグの push)。提出用リポジトリには `cloudbuild.yaml` と実行の記録を置く (提出用の org では Actions が使えない見込み)。GitHub との連携を足す時に改めて確認する
- 入口: QR コードから URL を開いてすぐ使える
- 公開の提出用リポジトリに載る Firebase のクライアント用のキー: Hosting のドメインと必要な API だけに制限し、README に「公開が前提のキーで、守りは Security Rules と ID トークンの検証」と書く
- 未定: デモ用の人物 (見られる側と見る人) の写真と手持ち。AI で作った架空の人物にする案
- 捨てた案: Next.js などで Web を別に作る (時間) / APK の配布 (審査員が Android を持つ前提で、1 台では近くに誰もいない) / ブラウザのエミュレータ (BLE が動かない)
